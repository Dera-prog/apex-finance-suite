Behaviour

Flows that survive the real world

Seven journeys, each mapped with the branch engineers usually find in production: expired codes, server refusals, dead connections, locked plans. Every write ends in either a server receipt or an explicit refusal — never a silent success.

Reading the diagrams. The numbered track is the happy path. Dashed branches underneath are alternative outcomes; steps marked fail are recoverable dead-ends that must offer a way back without losing the entered amount.

1 · Sign in with a phone code

First visit + returning Session 30 days
1
SplashBrand frame, then a single "Get started" action.
2
Phone entryCountry prefilled (+234), digit validation, "Send code".
3
Code entry6 cells, paste-to-fill, 30 s resend timer, "Verify".
4
Session storedToken saved; new phones get a zeroed ledger owner.
5
OverviewBalance skeleton for ~400 ms, then server state.
Branches
↳Wrong or expired code: cells shake once, inline "That code has expired. Request a new one." Timer resets to 0.
↳Rate limited (40 verifies / 10 min): "Too many attempts. Try again in 4 minutes." Submit disabled, countdown visible.
↳Offline: "Could not reach the Apex server." Primary becomes "Try again"; the phone number is kept.
↳No SMS provider configured (dev): a dismissible hint shows the code in-app; production hides it.

Card branch (sandbox)
↳POST /api/payments/checkout opens Paystack's hosted page. The app shows "Waiting for your bank…" and polls nothing — the signed webhook books PSK-…, then the app re-reads state on return.
↳Payment abandoned: returning to the app shows an unpaid state and leaves the balance untouched; retry reuses a fresh reference.
↳Amount outside ₦100–₦10,000,000: server refuses; message appears under the field.
↳Duplicate webhook: the PSK- reference is idempotent; the receipt shows once.
